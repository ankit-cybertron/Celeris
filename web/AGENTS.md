## What Lovable manages

Rules outside this block are the project's own. Change the pieces below in
Lovable, not by hand. With the [Lovable MCP](https://mcp.lovable.dev)
connected, `send_message` asks Lovable to do it; otherwise ask the user to
use the editor.

- **Database.** Do not add or edit `supabase/migrations/` or `drizzle/`.
  Ask Lovable to change the schema.
- **Generated files.** Do not edit a file whose header says it is automatically
  generated.
- **AI gateway.** Keep model calls on Lovable's gateway, and keep
  `LOVABLE_API_KEY` out of browser code.
- **Connectors.** Lovable provides native connectors. `list_connectors` shows
  which are enabled; `add_connector` only returns the dashboard link. When a
  connector is enabled, calls go through the connector gateway and need
  `LOVABLE_API_KEY`. When Lovable does not provide one, users can bring their
  own key and store it in Secrets.
- **Secrets.** Lovable manages them. Do not put secret values in the repo.

## Project rules

- All dashboard numbers come from static files in `public/data/*.json` (+ `submission.csv`), fetched client-side at startup by `src/lib/load.ts`; never hardcode figures in components. Why: the real competition outputs must drop in without code changes.
- Keep the data contract in `src/lib/types.ts` unchanged; the files currently in `public/data` are synthetic and regenerated by `scripts/generate_sample_data.py`. Why: the UI must accept the real files as-is.
- Aggregation over the cube lives only in `src/lib/engine.ts` (series masks, monthly sums, interval rule) and is memoised once per filter change in `DashboardContext`; views read `pts`/`stats` from context instead of looping the cube themselves. Why: the real cube is ~8 MB and must stay smooth.
- Every tab respects the five shared sidebar filters; name-keyed JSON rows are filtered with `matchRow` from `DashboardContext`. Why: filters are global by requirement.
- Chart colours come from CSS tokens (`--history`, `--forecast`, `--band`, `--chart-*`) via `C` in `src/components/dashboard/charts.tsx`. Why: one place for the history/forecast colour semantics.
- App settings (branding, default tab, theme mode/colour overrides, animation, filter labels, what-if and exception defaults) live in optional `public/data/config.json`, merged over `DEFAULT_CONFIG` in `src/lib/config.ts` and read from `DashboardContext.config`; never hardcode such defaults in views. Why: deployments retune the dashboard without code changes.
- Chart motion goes through `chartAnim()` from `src/lib/motion.ts` (spread onto every Recharts series), never literal `isAnimationActive`. Why: one switch for animation speed and reduced-motion.
